# 工单派活

你是调度的一方。实现代码不由你写：你写工单、派工单、检查交回来的东西。这样你的上下文不会被代码塞满，判断也不会被自己写的代码带偏。

只在用户要求时走这套流程，平时照常自己动手。

## 目录

```text
_tickets/
  open/      能马上开跑的工单（你写进来）
  doing/     已被领走的（dispatch.sh 挪过来；mv 是原子操作，挪成功就等于上了锁）
  done/      验收通过的（你验收后挪过来）
  blocked/   在等外部条件；在工单头写清等什么
  dropped/   放弃的；写清为什么
  templates/ ticket.md、receipt.md
  dispatch.sh  review.sh  workers.sh
_receipts/   <工单>.receipt.md、<工单>.review.md、日志
```

## 一、写工单

把 `_tickets/templates/ticket.md` 复制到 `_tickets/open/T<编号>-<短名>.md`，填好。

- **一张单只做一件事，对应一次提交。**几条命令说不清验收的，就拆开。
- **验收写命令，不写感觉。**比如「`cargo test health::` 全过」「`curl -s localhost:8080/api/x | jq .count` 输出 3」。工人必须原样贴出输出。
- **写清为什么这样验收。**工人可能过了检查却没达到目的（测试什么都没断言，防线守错了地方）。这一行告诉它，也告诉之后的审查员，真正要保住的是什么。
- **边界写明。**能动哪些文件；不提交；不挪工单。
- **写两张，派一张。**`open/` 里只放现在就能跑的。下一张通常取决于上一张回执里的存疑项。

## 二、派单

```bash
_tickets/dispatch.sh cursor:grok-4.7-xhigh            # 领 open/ 里最早的一张
_tickets/dispatch.sh agy:gemini-3.8-flash-high T4-fix-timezone
```

工人写成 `<cli>[:<模型>]`，支持哪些 CLI 看 `workers.sh`。一单要跑几分钟到几十分钟：放到后台跑，等它结束。读到回执之前，不要转述或猜测结果。

脚本会在工单上签下真实的 CLI 和模型，回执没法谎报是谁干的活。

## 三、验收（你来，不是工人）

读 `_receipts/<工单>.receipt.md`，然后自己核对。回执是说法，不是证据。

1. **每条验收命令自己重跑一遍**，和回执里贴的对比。
2. **看改动**（`git diff`、`git status`）：是不是只动了工单允许的？有没有删掉或改写不该动的东西？
3. **有实物就看实物**：打开页面、调一下接口、截个图。
4. 读存疑项。它常常是回执里最有用的部分。

不通过就写一张跟进单（T<编号>b），写清具体哪里失败，再派一次。不要自己悄悄修掉；失败的记录本身就有价值。

通过了就提交，一单一个提交，提交信息写上工单号。

## 四、换一家厂商审查

写代码的模型永远不审自己的代码。审查员换另一家：

```bash
_tickets/review.sh agy:gemini-3.8-flash-high T4-fix-timezone main..HEAD
```

审查员只读不改，报告落在 `_receipts/<工单>.review.md`。审已经提交的区间，不审还在变动的工作区。几张相关的单可以合起来审一次。

## 五、逐条核实审查意见

审查员经常看错。每一条：

- 打开它引用的文件和行号，确认问题真的存在。
- 成立：放进修复单（一张修复单可以包几条），派单、验收；修得多就再审一轮。
- 不成立：在报告下面写一行理由。

把你的核实结论追加在审查报告末尾，留痕完整。

## 六、收尾

把工单从 `doing/` 挪到 `done/`。告诉用户：什么现在能用了，哪些变化他可能会注意到，还剩什么风险。简短。

## 怎么选工人

- 施工和审查用不同厂商。它们犯的错不一样，这正是要的效果。
- 可以按数据敏感度分派：私密代码只交给你认可其隐私条款的工人，无所谓的活再给别的。
- 工人不挪工单、不提交、不审自己的活。
